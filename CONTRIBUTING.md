# Contributing

Issues help Ferrite most: bug reports, ideas, design suggestions and proposed fixes. Please open one on [GitHub issues](https://github.com/FerriteFW/ferrite/issues), or talk it over on the [Discord](https://discord.gg/fYygBVD2Kx) first.

## Issues: highly appreciated

- **Bugs:** what you did, what happened, what you expected. Add the version from About (MENU 0 9 8) and, for Console, your system.
- **Ideas and design:** the problem first, then how you'd like it to work. Sketches and screenshots are welcome.
- **Fixes:** describe the fix in an issue, with code if you have it. We'll build it in.

## Pull requests

Pull requests are welcome, with the contributor agreement.

- **The agreement:** read [CLA.md](CLA.md) and tick its box in the pull request template. Once, on your first pull request: it then covers everything you send to the project: Ferrite, Ferrite Console, the manual and the website. You keep your copyright; every published version stays public. Your name goes in [CLA-SIGNED.md](CLA-SIGNED.md).
- **Small and focused:** one fix or feature per pull request, with the issue it addresses. For anything big, open an issue first so we can agree on the approach.
- **Tested:** say how you checked it (the tests, a radio and which build, the simulator, a browser).
- **Never included:** anything from stock radio firmware, the SSB patch, recordings or flash dumps, or code under a licence that doesn't allow the agreement (such as the GPL).

## AI-generated pull requests

We'd rather have an issue than an AI-generated pull request.

- Ferrite is built with our own AI tools, which carry the project's context: the manual (the spec), the decision log, the tests and the hardware notes.
- A pull request from a tool without that context is hard to review and tends to miss why things are the way they are.
- The same idea as an issue gets in faster, and you're credited for it.
